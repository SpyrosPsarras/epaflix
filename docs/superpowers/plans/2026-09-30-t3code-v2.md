# T3 Code v2 implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use subagent-driven-development or executing-plans to implement this plan task-by-task. Steps use checkbox syntax for tracking. Execution method and implementation approval are pending.

**Goal:** Run a fresh v2 pod with v1 tool/access parity and hourly validated branch updates, without changing v1.

**Update 2026-10-01:** CI no longer builds from source. It takes the newest upstream preview release on the v2 branch, verifies its `linux-x64` archive against `SHA256SUMS` and builds the image from that (spec D7). Where this plan says branch build or source build, read preview archive.

**Architecture:** Create a separate v2 deployment in namespace `t3code`, reusing maintained tools and configuration inputs while keeping writable state independent. Validate branch-built candidates before publication and gate ArgoCD replacements on disconnected, idle v2 state. Native Arch packaging is a separate unresolved deliverable.

**Tech stack:** Existing Docker, GitHub Actions, GHCR, Kustomize, ArgoCD, Traefik, SOPS and MCP hub; Bash/Python/Node checks using existing tooling.

**Spec:** `docs/superpowers/specs/2026-09-30-t3code-v2-design.md`.

## Global constraints

- G1. StatefulSet `t3code-v2`, pod `t3code-v2-0`, namespace `t3code`, display name `T3 Code v2`; proposed endpoint `https://t3code-v2.epaflix.com`.
- G2. Preserve v1 deployment, endpoint, package pins and update behavior. No history migration or full-home copying; fresh identity, storage and pairing.
- G3. Initially clone all current v1 repositories, without worktrees or uncommitted files. Do not synchronize later project additions.
- G4. Keep maintained tools/configuration/access aligned with v1; distinct v2 MCP identity with equivalent permissions; no credentials in build inputs, images or logs.
- G5. Check `pingdotgg/t3code` preview releases hourly and take the newest one on branch `t3code/codex-turn-mapping`. Build changed previews or runtime inputs; deploy immutable validated candidates only with no clients and no active work.
- G6. Unknown activity blocks rollout. Guarded best-effort checks do not eliminate the last-check/restart race. Never force an update after a waiting timeout.
- G7. Failed candidates retain the running build; retry after source/input changes. Keep rollback image and recoverable v2 state backups.
- G8. Arch Linux x64 uses `/usr/bin/t3code-nightly`, owned by `t3code-nightly-bin 0.0.45_nightly.20260930.2468-1`. Keep it installed. Native v2 package delivery is undecided; no AppImage workflow is authorized.
- G9. Ask every question through the question UI. No commits, pushes, PRs or deployments without authorization. Before any authorized commit, check ancestry against current origin main and inspect status/diff/log.

## Review focus

- R1. Client/activity detection fails or upstream schema changes: retain the running pod. Task 4 tests unknown, malformed and incompatible observations.
- R2. Source changes while a build runs: publish the checked-out revision, not the latest remote branch head. Task 5 tests candidate provenance and stale promotion ordering.
- R3. Provider configuration in additional homes or expiring authentication: inventory every configured instance and report unsupported/auth-expired capabilities. Tasks 1 and 3 test complete inventory and selective provisioning.
- R4. Non-remote, missing or duplicate repository entries: record exceptions and avoid overwriting existing clones. Task 3 tests bootstrap classification and reruns.
- R5. An upgraded database is unreadable by the prior binary: stop new work and use a verified backup plus prior image. Task 6 rehearses recovery in isolated storage.

## Execution boundaries

Tasks 1 and 2 are prerequisite investigations. Read-only live inspection is permitted by their scope; source builds and synthetic runtime probes need execution approval. They must not deploy pods with production credentials.

Before Task 3, record the verified build command, client-count/activity interfaces, idle interval, storage/node sizing, secret-provisioning map and candidate-promotion method in the readiness report. Update this plan with exact interfaces supported by those findings and obtain approval through the question UI. If a requirement cannot be met, stop that branch and ask; do not silently weaken it.

The downstream tasks define intended deliverables and acceptance checks, not permission to guess the remaining mechanisms. Laptop Task 7 remains blocked until native packaging is separately selected. Server testing may finish before that decision, but the full user goal cannot be called complete.

- [ ] Add tests for zero activity, connected client, every active-work category, imminent schedule, malformed state, query failure and unsupported schema. Assert unknown states cannot be eligible. Run `python3 .../tools/rollout-ready.test.py` and confirm failure before implementation.

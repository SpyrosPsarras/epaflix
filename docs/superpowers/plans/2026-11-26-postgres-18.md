# PostgreSQL 18 upgrade Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move `postgres-cluster` from 16.15 on Debian 11 to 18 on Debian 13, load VectorChord as an image volume extension, and let Renovate keep the Postgres and VectorChord images current.

**Architecture:** Each step changes `postgres-cluster.yaml` in Git and Argo app `postgres` syncs it. First 16 on trixie (rolling), then 18 (CNPG offline `pg_upgrade --link`), then the `vchord` extension. Before the 18 window, app logins are blocked, a `pg_dumpall` goes to TrueNAS and a fresh base backup is taken.

**Tech Stack:** CloudNativePG 1.30.0, barman cloud plugin, Argo CD, Renovate 44.199.2 (regex managers), TrueNAS ZFS over `ssh truenas`.

**Spec:** `docs/superpowers/specs/2026-11-26-postgres-18-design.md`

## Global Constraints

- Every live step waits for the owner's yes. Task 3 is one window the owner picks, outside 02:00 to 06:00 Europe/Athens.
- Postgres image: `ghcr.io/cloudnative-pg/postgresql:<major>.<minor>-standard-trixie`, tag only, no digest.
- VectorChord image: `ghcr.io/tensorchord/vchord-scratch:pg18-v<x.y.z>@sha256:<digest>`.
- New barman `serverName`: `postgres-cluster-pg18`. The 16 path `postgres-cluster/` and the TrueNAS dump stay until the owner confirms 18.
- Never print or commit passwords. Use the superuser through `kubectl exec` on the primary's local socket only.
- PRs: conventional titles, rebased onto `origin/main`, merged by the owner. Argo app `postgres` syncs automatically (`selfHeal: true`, `prune: false`).
- Never touch namespaces `t3code-work` or `mcp-hub-work`.

## Review Focus

- An app role keeps an open session or reconnects through `postgres-pooler` after `NOLOGIN`. Task 3 checks `pg_stat_activity` has zero rows for the recorded roles before the dump.
- The role list recorded before the window is lost or wrong, so logins are not restored exactly. Task 3 writes it to a file in this pod and on TrueNAS, and the post-check diffs `rolcanlogin` against it.
- The dump stream breaks halfway (kubectl exec drop) and leaves a truncated file. Task 3 checks the completion line and the size.
- Renovate's regex also matches the README restore snippet or another file. Task 1's extract check expects exactly one `ghcr.io/cloudnative-pg/postgresql` dependency, from `postgres-cluster.yaml`.
- A CronJob that runs `pg_dump` with a 16 client fails after the upgrade. Task 3 runs `vaultwarden-backup` by hand afterwards and checks that it succeeds.

### Task 2: Rehearse the dump restore (live scratch test, no PR)

**Files:** none in Git. TrueNAS dataset `pithari/k8s/pg-upgrade`, created here and kept for Task 3.

**Interfaces:**
- Produces: dataset `pithari/k8s/pg-upgrade`, which inherits encryption from `pithari/k8s`. Produces the procedures `dump_to_truenas <name>` and `restore_from_truenas <name> <pod>` as written below, reused in Task 3.

This deviates from the spec on purpose. The dump runs inside the primary instead of a Job, so its `pg_dumpall` always matches the server version and no image or NFS share is needed.

The rehearsal on 2026-11-26 changed the method. Streaming `pg_dumpall` through `kubectl exec` broke after 87 s with an API `i/o timeout` and left a 1.1 GB dump with no completion line. The working method: `pg_dumpall` runs in the background inside the primary and writes next to `pgdata` on its `local-path` volume. Then the file is copied from the node over SSH, gzipped on the way to TrueNAS, and checked by sha256. The restore copies the file onto the target pod's volume the same way and runs `psql -f` in the background. Measured: dump 103 s, dump plus copy 181 s, restore 93 s. The only restore errors were the three CNPG roles that already exist (`postgres`, `streaming_replica`, `cnpg_metrics_exporter`).

- [ ] **Step 1: Create the dataset.** `ssh truenas 'sudo zfs create pithari/k8s/pg-upgrade && zfs get -H -o value encryption,keystatus pithari/k8s/pg-upgrade'`. Expected: `aes-256-gcm`, `available`.
- [ ] **Step 2: Dump.** Use name `rehearsal-<date>`.
  `dump_to_truenas <name>`:
  1. Check for `<name>.*` in the primary's volume, and go on only when the check runs and finds nothing. Otherwise pick a new name or retry the check. In the primary, under `umask 077`, start `pg_dumpall -U postgres > /var/lib/postgresql/data/<name>.sql` in a background subshell that ignores HUP. The subshell writes the exit code to `<name>.rc`.
  2. Poll `<name>.rc` with short `kubectl exec` calls. Stop if the exit code is not 0 or the last 200 bytes lack `PostgreSQL database cluster dump complete`. Keep the source file in both cases.
  3. From the primary's node (`spec.local.path` of its PV), copy the file over `ssh`. Pipe it through `gzip`, then to `ssh truenas` with `umask 077` and `set -o noclobber`. That writes `/mnt/pithari/k8s/pg-upgrade/<name>.sql.gz` with mode `0600` and refuses to overwrite.
  4. `gzip -t` the copy on TrueNAS, then compare the source's sha256 with `zcat | sha256sum` on TrueNAS. Delete the source file only if both pass.
- [ ] **Step 3: Start a throwaway cluster.** Namespace `pg-rehearsal`, Cluster `pg-rehearsal`, 1 instance, image identical to live, `local-path` 20Gi, no `plugins:` block, no superuser secret. Let CNPG generate one and keep `enableSuperuserAccess: true`.
- [ ] **Step 4: Restore.**
  `restore_from_truenas <name> <pod>`: `zcat` the file on TrueNAS and pipe it over `ssh` into `<pod>`'s volume folder on its node, under `umask 077` and owned by uid 26. Then run `psql -U postgres -X -q -f` on it in a background subshell that ignores HUP, with its output and errors in `0600` files, and poll for its exit code. A zero exit code does not prove success, because `psql -f` continues after SQL errors, so check the error log. Delete the restore file and logs afterwards.
  The only allowed errors are `role ... already exists` for `postgres`, `streaming_replica` and `cnpg_metrics_exporter`. Show any other error text to the owner.
- [ ] **Step 5: Compare.** The database list (`select datname from pg_database order by 1`) and `count(*)` on the 10 largest tables (by `pg_total_relation_size`, across all databases) match live. Write the live numbers to `./pg-rehearsal-counts.txt`.
- [ ] **Step 6: Clean up.** `kubectl delete ns pg-rehearsal`, remove the rehearsal dump from TrueNAS and the counts file. The dataset stays. Report the dump size and the restore time to the owner. This sets the expectation for the window.

### Task 3: The 18 window (PR prepared ahead, live window)

**Files:**
- Modify: `2-k3s/06.postgres/cluster/postgres-cluster.yaml` (`imageName`, plugin `parameters.serverName`)
- Modify: `2-k3s/26.vaultwarden/kustomization.yaml:47-48` (`postgres` to `18.<minor>-trixie@sha256:<digest>`, Docker Hub official image)
- Modify: `README.md` "Postgres restore" (restore image to the 18 tag, `serverName: postgres-cluster-pg18`, next free path `postgres-cluster-pg18-2`)

**Interfaces:**
- Consumes: `dump_to_truenas` from Task 2 (`restore_from_truenas` only for a rollback), dataset `pithari/k8s/pg-upgrade`.
- Produces: the cluster on 18 with backups in `postgres-cluster-pg18`. Files `./pg18-login-roles.txt` and `./pg18-counts.txt` in this pod, deleted after the owner confirms.

- [ ] **Step 1: Prepare the PR** with the three file changes. Title: `feat(postgres): upgrade to PostgreSQL 18`. The body lists the window procedure and the rollback. Do not merge. If Renovate has opened its own 18 PR, ask the owner, then close it with a comment that points to this PR.
- [ ] **Step 2: Owner yes and window time.** Confirm the time is not between 02:00 and 06:00, and that no `vaultwarden-backup` Job is active.
- [ ] **Step 2b: Take a backup** named `pg16-final` (as in Task 1, Step 9) and wait for `completed`. This runs before logins are blocked because it takes about 13 minutes, and the WAL archive covers the writes until the shutdown.
- [ ] **Step 3: Record login roles** on the primary: `select rolname from pg_roles where rolcanlogin and not rolsuper and rolname <> 'streaming_replica' and rolname not like 'cnpg\_%' order by 1`. CNPG owns the `cnpg_` roles. Blocking app roles is enough, because the pooler logs in to the server as the app role. Save to `./pg18-login-roles.txt` and copy it to `/mnt/pithari/k8s/pg-upgrade/`.
- [ ] **Step 4: Block logins.** `ALTER ROLE <r> NOLOGIN` for each recorded role, then `select pg_terminate_backend(pid) from pg_stat_activity where usename = any(<list>)`. After 10 seconds, `select count(*) from pg_stat_activity where usename = any(<list>)` must be `0`.
- [ ] **Step 5: Record the counts** for the 10 largest tables to `./pg18-counts.txt`.
- [ ] **Step 6: Dump** with `dump_to_truenas pg16-final-<date>`.
- [ ] **Step 7: Archive the last WAL (best effort).** On the primary, run `select pg_walfile_name(pg_switch_wal())`. Wait until `pg_stat_archiver.last_archived_wal` is that segment or later and `last_failed_time` has not moved. Also check that nothing could have archived out of order: the primary is the same as at `pg16-final`, its timeline has not changed, and `pg_postmaster_start_time()` is earlier than the backup. This makes it very likely that the 16 archive holds every write up to the freeze, but it does not prove it: a backend crash can leave a segment unarchived without any of these signs. The verified dump from Step 6 is the rollback copy. The WAL archive is a best-effort second copy.
- [ ] **Step 8: Owner merges the PR.** Watch the cluster status and the `*-major-upgrade` Job. CNPG stops all pods, runs `pg_upgrade`, then starts the primary. Wait for `Cluster in healthy state` with 3 ready instances.
  On Job failure: revert the PR, wait for the cluster to be healthy on 16, run `ALTER ROLE <r> LOGIN` for the recorded roles, tell the owner, stop.
- [ ] **Step 9: Allow logins again.** `ALTER ROLE <r> LOGIN` for exactly the roles in `./pg18-login-roles.txt`. Run the Step 3 query again and diff it against the file: no difference.
- [ ] **Step 10: Finish the upgrade.** If `/var/lib/postgresql/data/pgdata/update_extensions.sql` exists on the primary, run it with `psql -U postgres -f`. Then run `vacuumdb -U postgres --all --analyze-in-stages`.
- [ ] **Step 11: Take a backup** named `pg18-first`. Wait for `completed`. `kubectl -n postgres-system get objectstore postgres-minio-store -o jsonpath='{.status.serverRecoveryWindow}'` shows `postgres-cluster-pg18` with a recent `lastSuccessfulBackupTime`.
- [ ] **Step 12: Check.**
  - `select version()` starts with `PostgreSQL 18`.
  - 27 databases.
  - Counts equal `./pg18-counts.txt`.
  - `kubectl -n argocd get applications` shows every app Healthy, the same as before the window.
  - `kubectl -n vaultwarden create job --from=cronjob/vaultwarden-backup pg18-check` completes successfully. Delete that Job afterwards.
- [ ] **Step 13: Report** the downtime from Step 4 to Step 9 and every check result. Ask the owner to confirm 18. Rollback after this point follows the spec: restore from the dump or recover from `postgres-cluster`, decided with the owner.
